# Card Manifest — единый документ

**Статус:** сводка текущего состояния + направление. Согласуется. Заменяет разрозненные
документы по карточкам устройств (список к удалению — в конце).

Этот файл — единственный источник по теме «карточка устройства из декларации сущностей».
Схема формата остаётся машинной в `contracts/mqtt_contract.yaml`; здесь — смысл, состояние,
план. При расхождении с yaml прав yaml.

---

## 1. Идея в одном абзаце

Устройство описывает себя **списком сущностей в модели Home Assistant**
(`sensor` / `binary_sensor` / `number` / `select` / `button` / `climate`). Портал и
приложение строят карточку из этого списка. Данные и команды идут по **существующим**
топикам (`telemetry` / `status` / `commands/invoke`) — новых форматов данных не плодим.
Модель HA выбрана не случайно: она уже проверена, и одно объявление устройства понимают
и портал, и приложение, и сам Home Assistant.

## 2. Два пути карточек (решение принято)

1. **Свои продуктовые карточки** — `HeaterCard` / `StorageCard` / `IDryerCard`
   (`frontend-v2/src/components/dashboard/cards/`). Ручная вылизанная вёрстка под наши
   изделия. Уже в проде. **Не трогаем и не переводим на манифест.**
2. **Авто-карточки из манифеста** — `EntityDeviceCard`
   (`frontend-v2/src/components/device/entity/`). **Для сообщества**: сторонних устройств
   на нашем SDK. Строятся из card-манифеста. Два режима: авто-раскладка и разметка `layout`.

**Правило выбора** (`DeviceDashboardCard.tsx`): `deviceType` — **один из наших продуктов**
(IHEATER_LINK / STORAGE_LINK / DRYER / HEATER) → своя карточка; **любой другой** (UNKNOWN
или будущее чужое значение) + есть `cardManifest.entities` → авто-карточка; иначе →
нейтральный fallback. Проверяем «наш ли тип», а не конкретную строку `UNKNOWN` — правило
переживёт появление новых типов.

## 3. Модель сущностей (как в HA)

| Тип | Смысл | Как значение уходит на устройство (из семантики HA) |
|---|---|---|
| `sensor` | показать значение | ничего не шлёт (read-only) |
| `binary_sensor` | вкл/выкл, открыто/закрыто | ничего не шлёт (read-only) |
| `number` | числовой контрол | **по изменению значения**, без отдельной кнопки «отправить» |
| `select` | выбор из списка | **по выбору** |
| `button` | разовое действие | **по нажатию** |
| `climate` | составной термостат (сложное устройство) | встроенный домен HA; см. §8 (план «может когда-нибудь») |

- `device_class` (temperature / humidity / carbon_dioxide / weight / power…) несёт
  единицу и иконку. Иконку **задаёт device_class** (как в HA: temperature→термометр,
  humidity→капля). Для сенсора без известного класса — общий fallback-значок (остаётся).
- Как именно уходит значение — **свойство типа сущности**, а не устройства и не произвол
  рендерера. Отдельной кнопки «отправить» у `number` в модели HA нет.

## 4. Транспорт (существующий, не новый)

- **Данные сенсоров:** `idryer/{serial}/telemetry` (`units[]`), плюс кастомные поля
  продукта через `Link::onTelemetryPublish`. Путь к значению — поле `path` сущности
  (например `units[0].vocIndex`).
- **Команды контролов:** `idryer/{serial}/commands/invoke`, payload
  `{action, unitId, args, timestamp}`. Это тот же канал, которым идут `heat.start`,
  `led.pulse`. У community-контрола `action = "card.{id}"`, SDK по нему зовёт колбэк.

## 6. Текущее состояние — честно

### Есть и работает
- Навыки: `capability_vocabulary` + публикация в `/info`; авто-сенсоры из `Config.has*`.
- Топик `card` (retained) + `CardBuilder`; backend принимает/санитизирует/хранит
  (`Device.cardManifest`), отдаёт в device-response, шлёт `device:refresh` при изменении.
- `EntityDeviceCard` рендерит `sensor` / `binary_sensor` / `number` / `select` / `button`;
  дашборд роутит `UNKNOWN`+манифест на неё.
- Команды: `commands/invoke` — рабочий канал (наши продукты и community на одном канале).
- **HA-модель уже реализована в прошивке**: `ha_publisher` (sensors/binary_sensor c
  `device_class`) + `ha_builder` (`number` min/max + `command_topic`, `select` options,
  `button`) — см. §9 контракта.

### Нет
- Продукты **не объявляют свои контролы** в card-манифесте → реальные манифесты тощие
  (у iHeater только `power`). Богатые карточки видели только на выдуманных данных.
- Составной `climate` не реализован — сложное устройство пока = набор примитивов.
- **Дублирование объявления сущностей**: две параллельные декларации одного и того же —
  `CardBuilder` (топик `card`) и HA-discovery (`ha_builder`/`ha_publisher`). Концепция
  требует ОДНУ модель (см. §7).

### Убрано из кода (мой лишний UI, которого нет в модели HA/спеке)
- Кнопка-подтверждение `CheckIcon` (✓) у `number` — удалена; `number` шлёт по изменению
  (дебаунс).
- Принудительный side-by-side контролов в ряду `layout` — убран; контролы во всю ширину.
- `buildStubManifest` — лабораторный (только `/cards-lab`), в проде не участвует.

**Оставлено намеренно:** общий fallback-значок для сенсора без известного `device_class`
(нормальная деградация, когда класс не распознан).

## 7. Главное расхождение к устранению

Сейчас модель сущностей объявляется **дважды**: в HA-discovery (прошивка, `ha_builder`/
`ha_publisher`) и в card-манифесте (`CardBuilder`). Это ровно то дублирование, которое
концепция запрещает.

**Направление:** одна HA-модель — источник, второе — проекция. Практично: card-манифест
для портала/приложения и HA-discovery для Home Assistant **генерятся из одного описания
сущностей** (в идеале через контракт/кодоген, как остальные артефакты). Итог: продукт
объявляет сущность один раз (`ha.number(...)` / `card().number(...)` сводятся к одному
API), и её видят все три потребителя.

## 8. Принципы внедрения (решено 2026-08)

1. **Как можно проще.** Не изобретаем свою модель — берём модель HA (проверенную).
2. **База — совместимость с HA.** Устройство описывает себя один раз в HA-совместимом
   виде; HA понимает это из коробки.
3. **Портал строится на том же.** Портал/приложение читают то же самое описание —
   отдельного «своего» формата не заводим.
4. **Не ломаем существующие карточки.** Ручные `HeaterCard`/`StorageCard`/`IDryerCard`
   остаются как есть. Всё ниже — «под капотом» + для community-устройств.
5. **`climate` — отклонено.** Не нужен: температура/влажность/мощность и т.п. — обычные
   отдельные сущности, отдельный «термостат»-домен не заводим.

## 9. План (без сроков, порядок)

1. **Одно объявление вместо двух.** Продукт объявляет сущность **один раз**; SDK сам
   отдаёт её и в HA-discovery (для Home Assistant), и в `card` (для портала). Убирает
   дублирование `ha_builder`/`ha_publisher` ↔ `CardBuilder` (§7). Единый product-API
   вместо пары `ha.number()` / `card().number()`.
2. Как следствие п.1 — продукты объявляют свои контролы, манифест перестаёт быть тощим
   (сейчас у iHeater только `power`).
3. Иконки по `device_class` (набор классов и дефолтных иконок — как в HA; fallback-значок
   для неизвестного класса оставлен).
4. ✅ Убрать лишний UI из `EntityDeviceCard` (сделано: number по изменению, контролы во
   всю ширину, стаб — лабораторный).
5. Мобилка — тот же рендер из манифеста. **На потом, после согласований.**

## 10. Детали реализации рендерера (для портала и мобилки)

Эталон: `frontend-v2/src/components/device/entity/entity-manifest.ts` (маппинг
манифест→сущности) + `EntityDeviceCard.tsx` (рендер). Flutter зеркалит логику, вёрстка своя.

### 10.1 Схема сущности (гарантии после санитизации backend)

```jsonc
{
  "v": 1,
  "entities": [ /* 1..32, id уникальны */ ],
  "layout":   [ /* опционально, ≤16 рядов по ≤4 id, только существующие id */ ]
}
```

| Поле | Тип/формат | Когда есть |
|---|---|---|
| `id` | `[a-z0-9_]{1,24}` | всегда, уникален |
| `type` | `sensor \| binary_sensor \| number \| select \| button` | всегда |
| `device_class` | `[a-z0-9_]` | опц. — семантика словарного сенсора |
| `label` | printable ASCII ≤32 | опц. (у словарных обычно нет — потребитель переводит) |
| `unit` | ASCII ≤8 (+°²³) | опц. |
| `source` | `telemetry \| status` | у sensor/binary_sensor всегда |
| `path` | JSON-путь ≤48, напр. `units[0].vocIndex` | у sensor/binary_sensor всегда |
| `action` | `[a-z0-9_.]{1,32}`, обычно `card.{id}` | у number/select/button всегда |
| `arg` | имя аргумента, дефолт `value` | у number/select |
| `min`/`max`/`step` | числа, min≤max | у number |
| `options` | 1..8 строк ASCII ≤32 | у select, непустой |

### 10.2 Маппинг типа на виджет

- `sensor` со словарным `device_class` (`temperature`, `humidity`, `heater_temp`,
  `power`) → штатная ячейка с локализованной подписью и иконкой потребителя
  (label из манифеста игнорируется в пользу перевода);
- `binary_sensor` со словарным классом (`fan`, `servo`) → двоичная ячейка;
- `sensor`/`binary_sensor` без словарного класса → генерик-ячейка: `label ?? id`,
  `unit`, значение по `path`, «—» пока данных нет (иконка — fallback-значок);
- `button` → кнопка (шлёт по нажатию); `number` → поле min/max/step (шлёт **по
  изменению**, дебаунс, без кнопки-submit); `select` → список (шлёт по выбору).

### 10.3 Раскладка

- **Слой 1 (нет layout):** порядок = порядок `entities[]`; подряд идущие
  ячейки-сенсоры группируются в ряды **по ≤3** (4-я переносится); контролы —
  **каждый во всю ширину**, разрывают ряд ячеек.
- **Слой 2 (есть layout):** каждый ряд `layout` → горизонтальный ряд из ячеек;
  контролы всё равно во всю ширину (в один ряд не жмём); сущности не из layout
  дорисовываются ниже правилом слоя 1.

### 10.4 Живые значения (`path` → данные)

- Снапшот: REST-ответ юнита (словарные поля `temperature`/`humidity`/`fanStatus`…).
- Live: WS `telemetry:update` `{deviceId, unitId, data}` — `data` содержит словарные
  поля + **кастомные примитивы юнита как есть** (backend пробрасывает ≤16
  number/boolean, напр. `vocIndex`).
- Резолв `path` для WS-данных: событие уже пер-юнитное и плоское → берём
  **последний сегмент** пути: `units[0].vocIndex` → ключ `vocIndex`. (Полный
  JSON-путь нужен только консьюмерам сырого MQTT, напр. HA-генератору.)

### 10.5 Устойчивость рендерера

Backend санитизирует, но рендерер терпим: неизвестный `type`/`device_class` →
**пропустить сущность** (не падать); нет значения → «—»; `label` — только plain
text (без HTML/markdown).
